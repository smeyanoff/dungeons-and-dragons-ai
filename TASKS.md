## 🔴 P0 — Блокеры (влияют на базовый UX/геймплей)

### P0.1 ⏳ Ability checks: перейти на **текстовый** `/roll` (убрать зависимость от inline‑кнопок)
- **Почему:** сейчас pending check резолвится через inline callback (`ability_roll_*`) и игроку предлагается “нажать кнопку” — это расходится с продуктовым требованием “только текст” и ломает UX.
- **Что сделать:**
  - В `internal/telegram/bot.go`:
    - если **есть pending check** и игрок пишет `/roll` (или `/roll d20`) → резолвить **именно pending check** через `performAbilityCheckUC.Execute(ctx, chatID)` и очищать pending check;
    - если **нет pending check** и игрок пишет `/roll ...` → **не** пытаться резолвить check; выполнять обычный бросок кубика (или отвечать нейтрально, если это “голый результат” без выражения);
    - поддержать “ручной ввод результата” (например: `результат 17` / `17`) **только когда pending check существует** (оффлайн‑кубики).
  - Перевести `maybeSendPendingAbilityCheckPrompt` на **текстовую** подсказку (“🎲 Проверка … Напиши `/roll d20`”), без кнопок.
  - Обновить/добавить интеграционные тесты:
    - `tests/integration/telegram_tool_first_ability_check_flow_test.go`: сценарий без callback, через `/roll`.
    - `tests/integration/ability_check_guardrails_test.go`: `/roll` без pending check не резолвит проверку.
- **Критерии приемки:**
  - Pending check создаётся через `request_ability_check`, а резолвится **только** текстовым `/roll` (и ровно один раз).
  - Никаких inline‑кнопок для проверок.

### P0.2 ⏳ Guardrails против спама проверок: budget + anti‑trivial + обязательные reason/stakes (runtime)
- **Почему:** промпт‑правила недостаточны, нужен runtime‑контроль (см. `PRODUCT_IDEAS.md` + сигналы из `FEEDBACK.md`).
- **Что сделать (минимум):**
  - Ввести “budget” существенных проверок на сцену/короткий промежуток (хранить в сессии/истории).
  - Anti‑trivial: низкие ставки → автоуспех/описание без броска (и запись в историю как decision).
  - Обязательные `reason` + `stakes`: если пусто — отклонять запрос проверки или заменять безопасным шаблоном и логировать.
  - Логи/метрики: почему check отклонён (budget/cooldown/trivial/missing_fields).
- **Критерии приемки:**
  - DM физически не может “зафлудить” проверками без эскалации ставок.
  - Интеграционные тесты фиксируют максимум проверок на коротком сценарии.

### P0.3 ⏳ DM Analyzer: `{}` / пустой анализ = ошибка контракта (retry + skeleton), иначе ломаются триггеры
- **Факт в коде сейчас:** пустой анализ логируется (`analyzer_empty_json_rate`) и приводится к “ничего не делаем”.
- **Что сделать:**
  - Считать empty analysis причиной для retry (как `invalid_json`/`invalid_schema`), с ужесточённым промптом + обязательным skeleton JSON.
  - После исчерпания ретраев — применять **детерминированный fallback** для критичных триггеров (минимум: бой по явным маркерам).
  - Добавить интеграционный тест: в сценарии, где ожидается триггер, анализатор не может “тихо” вернуться пустым без fallback.
- **Критерии приемки:**
  - В проде `analyzer_empty_json_rate` стремится к 0; при деградации есть явный fallback.

### P0.4 ⏳ Truncation контекста перед LLM: зафиксировать бюджет и приоритеты + лог “что выкинулось”
- **Источник:** `CODE_REVIEW.md` (truncated prompt).
- **Что сделать:**
  - Явно определить приоритеты блоков контекста (инструкции, текущая локация, последние N story events, активный бой/квесты, pending check).
  - При truncation логировать, какие top‑level блоки были удалены.
- **Критерии приемки:**
  - В UX “несколько ходов + перемещения” DM стабильно учитывает локацию/выходы/активные события.

### P0.5 ⏳ `/map`: graceful fallback при 429/timeout на генерации изображения + кеширование
- **Что сделать:**
  - Если image generation не удалась → всегда возвращать **текстовую карту** (и навигацию).
  - Кешировать карту мира и не генерировать заново при каждом `/map`.
- **Критерии приемки:**
  - `/map` всегда даёт полезный ответ (минимум текст), даже при 429.

### P0.6 ⏳ RAG/infra: Qdrant healthcheck/monitoring не должен дергать `/health` (404)
- **Что сделать:**
  - Привести healthchecks/мониторинги к `/healthz` или `/readyz`.
  - Убедиться, что prod‑контейнеры пересозданы с актуальным `build/docker-compose.prod.yml`.
- **Критерии приемки:** нет 404 в логах Qdrant на `/health`, контейнер `healthy`.
