## 🔴 P0 — Блокеры (влияют на базовый UX/геймплей)

### 1) Усечение контекста перед LLM → DM “не видит” часть мира/истории
- **Доказательство (prod log, 2026-01-21):** `Game context truncated for prompt ... original_length=22618 ... max_context_length=16000`.
- **Риск:** пропуски локаций/связей/событий → деградация RAG и непредсказуемые ответы DM.
- **Action items:**
  - Жёстко зафиксировать бюджет и приоритеты контекста (что должно попадать всегда): *инструкции*, *текущая локация*, *последние N story events*, *активные квесты/бой*.
  - Сжать/переформатировать “ability checks” и справочные блоки (держать максимально компактными).
  - Добавить метрику/лог “что именно выкинулось” (top-level блоки) при truncation, чтобы было понятно, что теряем.
- **Как проверить:** в `dnd-bot-prod` предупреждение `Game context truncated...` становится редким; в UX сценарии `/newgame` → несколько ходов → `/map`/перемещения DM стабильно учитывает текущую локацию/выходы/активные события.

### 2) Ability checks: сейчас завязаны на inline‑кнопку/callback → расходится с “только текст” и мешает guardrails
- **Факт в коде (2026-01-21):** pending ability check показывается как “Нажмите кнопку…” и резолвится через callback `ability_roll_*` (см. `internal/telegram/bot.go`).
- **Риск:** UX ломается (не текстовый), игрок “учится” кнопкам, а не механике `/roll`; сложнее ограничивать частоту и объяснять правила.
- **Action items:**
  - Перевести резолв pending check на текстовый `/roll` (и ручной ввод результата только при pending check).
  - Убрать inline‑кнопку для проверок (оставить только текстовую подсказку).
  - Добавить/обновить интеграционные тесты: `/roll` без pending check не резолвит ничего; `/roll` с pending check резолвит ровно один раз.
- **Как проверить:** tool-first сценарий ability check проходит без callback; player‑facing сообщения не содержат “нажмите кнопку”.

### 3) DM Analyzer: пустой анализ (`{}` / “ничего не найдено”) не должен тихо гасить триггеры
- **Доказательство (prod log, 2026-01-21):** `[DM Analyzer] Raw LLM response ... {}` + счётчики `analyzer_json_empty_json`, `analyzer_empty_json_rate`.
- **Текущее состояние:** метрика/лог есть, но empty analysis приводит к “skip state changes” без ретрая → триггеры теряются.
- **Action items:**
  - Считать empty analysis **ошибкой контракта** и делать retry с ужесточённым промптом + обязательным skeleton JSON.
  - После ретраев — детерминированный fallback для критичных триггеров (минимум: бой).
  - Интеграционный тест: в сценарии “должен стартовать бой/квест” анализатор не может “молча” вернуть пусто без fallback.
- **Как проверить:** `analyzer_empty_json_rate` близок к 0; в UX бой/квесты стартуют при ожидаемых входах, даже при деградации анализа.

### 4) `/map` зависит от генерации изображения и падает на rate limit → UX “карты” ломается
- **Доказательство (prod log, 2026-01-21):** `GigaChat: Rate limited (429)` (3 ретрая) → `Failed to generate world map image ... context deadline exceeded`.
- **Риск:** игрок нажимает `/map` и не получает полезного результата/навигации; повторные попытки усиливают rate limit.
- **Action items:**
  - Сделать **graceful fallback**: если image generation не удалась → отправлять **текстовую карту** (навигация — текстовая или временно inline, но без зависимости от картинки).
  - Кешировать/переиспользовать карту мира; не генерировать заново при каждом `/map`.
  - Добавить явный rate limit/очередь на image generation (отдельно от LLM текста) и увеличить наблюдаемость (код/таймаут/кол-во ретраев).
- **Как проверить:** `/map` всегда возвращает полезный ответ (хотя бы текст+кнопки), даже при 429 от провайдера изображений.

## 🟠 P1 — Стабильность/качество/UX

### 1) “Проверки нельзя починить промптом”: нужны runtime‑guardrails (budget/cooldown/anti‑trivial)
- **Сигнал:** `FEEDBACK.md` — ожидание игроков: проверки редкие и значимые.
- **Action items:**
  - Runtime guardrails вокруг `request_ability_check`: budget/cooldown/anti-trivial + обязательные `reason`/`stakes`.
  - Запрет на player-facing “используй /roll …” без реального запроса проверки (DM должен инициировать проверку только tool-вызовом).
- **Как проверить:** в интеграционном прогоне описательные запросы не приводят к “/roll d20”; число проверок на короткий отрезок ограничено.

### 2) `/battlefield` нестабилен/непрозрачен (сложно отлаживать бой)
- **Сигнал:** `FEEDBACK.md`.
- **Action items:** сделать вывод состояния боя детерминированным и покрыть тестами (минимум: текущие участники, HP, эффекты, чей ход).
- **Как проверить:** `/battlefield` работает в e2e сценарии боя и помогает воспроизводить баги.

## 🟡 P2 — Операционка/шум (не ломает игру напрямую, но мешает)

### 1) Qdrant: внешний мониторинг дергает `/health` (404)
- **Доказательство (qdrant log, 2026-01-21):** `GET /health ... 404` (внешний IP).
- **Action items:** в мониторингах/healthchecks использовать **`/healthz` или `/readyz`**, не `/health`.
- **Как проверить:** в логах Qdrant нет 404 на `/health`; алерты/healthchecks зелёные.

### 2) Шумные `record not found` от GORM (и ANSI-цвет в логах)
- **Доказательство (prod log, 2026-01-21):** `record not found` из `persistence/player.go:30`, `persistence/combat.go:25`.
- **Action items:** не логировать `ErrRecordNotFound` как error-level; отключить ANSI-раскраску/привести GORM логи к zap-формату.
- **Как проверить:** “красных” блоков `record not found` больше нет, остаются только реальные ошибки.

### 3) InitCampaign: невалидный JSON от LLM → repair/retry (нестабильность контракта)
- **Доказательство (prod log, 2026-01-21):** `LLM response for locations is not valid JSON, attempting to repair` → `Failed to repair ... retrying`.
- **Action items:** ужесточить JSON-контракт (schema + примеры), уменьшить свободу формата; поднять наблюдаемость (сколько repair/retry на сессию).
- **Как проверить:** в норме генерация мира проходит без repair/retry (или с 1 редким ремонтом), без каскадных ретраев.
