# Продуктовые идеи для D&D AI Telegram Bot

**Последнее обновление:** Январь 2026  
**Product Manager:** AI Agent

## Что уже есть (контекст)
- **MVP**: одиночная D&D‑подобная кампания в Telegram с AI Dungeon Master.
- **RAG/память**: события/история индексируются и подмешиваются в контекст.
- **Системы**: персонаж, инвентарь/вес, бой (инициатива/урон), квесты, карта, генерация мира.
- **DM tools**: function calling (в т.ч. кубики/follow‑ups).
- **Карта**: `/map` + текстовая карта; навигация сейчас реализована через inline‑действия (`map_to_*`), текущая локация хранится в сессии. **Целевой UX — полностью текстом**.
- **События локаций**: генерация при посещении (типы `WorldEventTypeLocation*`) и структурированная `metadata` (hook/options/suggested_checks/stakes/status); событие фиксируется в истории и индексируется в RAG, чтобы DM “видел” его в контексте.

## Главный приоритет (сейчас): события локаций → проверки → бросок кубика игроком (tool-first, не prompt-first)

### Почему это важно
- **Prompt‑правила не работают**: DM начинает **спамить проверками**, ломает темп и раздражает игрока.
- Нужен контроль на уровне **tools + runtime guardrails**, а не “пожеланий” в промпте.

### Product goal
- Проверка — это **осознанный вызов DM tool** (DM решает *когда*), а система обеспечивает:
  - **удобный бросок текстом** (без кнопок),
  - **контекст и ставки** (reason/stakes обязательны),
  - **ограничители частоты** (budget/cooldown/anti‑trivial).

### Принцип UX (жёсткое требование)
- **Только текст**: игрок взаимодействует с миром и механиками **сообщениями**, без кнопок/inline‑UI.
- Проверка должна выглядеть для игрока как короткая реплика DM + понятная команда/фраза для броска (без “регламентов”, таблиц DC и списков “предопределённых проверок” в тексте сцены).
  - Примечание: часть текущей реализации (карта, pending check) всё ещё использует inline‑кнопки; цель спринта — убрать зависимость от кнопок для проверок (см. `TASKS.md` → P0.1).

### Ключевое правило механик (P0): игрок НЕ может инициировать проверку “через DM”
- **Только система** (через DM tool `request_ability_check`) имеет право создать **pending ability check**.
- Игрок может бросать кость **только если есть pending check**; иначе `/roll` (или “15”, “бросаю d20”) не должен запускать проверку/резолв.
- DM не должен “вести механику в тексте”: никаких “Выполняется проверка…”, “Оцениваем результат…”, “✅ УСПЕХ!” как служебной трассировки.
- DM не должен принимать “голый результат” (`15`) как бросок, кроме явно разрешённого режима ручного ввода (и только когда pending check существует).

**Acceptance criteria (поведение бота):**
- Если **нет** pending check и игрок пишет `/roll` / “roll d20” / “15”:
  - бот отвечает нейтрально: “Сейчас проверка не требуется. Что ты делаешь?” (и продолжает сцену), **без** резолва проверок.
- Если pending check **есть**:
  - `/roll` резолвит **только этот** pending check (один раз), пишет результат в историю и очищает pending check.
  - повторный `/roll` без нового pending check не резолвит ничего.

### Анти‑паттерны, которые нужно запретить (player-facing)
- DM пишет “**Используй `/roll d20`, если хочешь узнать больше деталей**” как дефолтный способ исследования.
- DM вставляет в сцену “**Инструкцию по проверкам**”, таблицы DC, “predefined checks”, или рассуждения “почему сейчас проверка нужна/не нужна”.
- DM говорит “эти проверки важны для продвижения” и тем самым **гейтит контент дайсом** (провоцирует спам проверок).

### Как должно быть вместо этого (текстовый UX без кнопок)
- DM завершает сцену вопросом “Что ты делаешь?” и, если нужно, даёт 2–4 **варианта действий текстом** (например, нумерованный список), но без принуждения к проверке.
- Проверка появляется **только как реакция на конкретное действие игрока** и инициируется через `request_ability_check` (с краткими `reason+stakes`).

### Что уже есть / чего не хватает
- **Есть**:
  - DM tool `request_ability_check`;
  - **pending ability check в сессии** (сохранение ожидания проверки и привязка к следующему броску);
  - запись результата броска/проверки в историю и индексация событий в RAG;
  - генерация location events при первом посещении локации (как `world_events`) со структурированной `metadata`;
  - пайплайн видимости события локации: `world_event` → `story_event` → индексация в RAG → попадание в контекст DM.
- **Не хватает (актуальный gap)**:
  - текстового UX броска для pending check: резолв через `/roll`, advantage/disadvantage и ввод результата вручную (оффлайн‑кубики);
  - guardrails уровня runtime: **budget** и **anti‑trivial** поверх уже существующих ограничителей;
  - “жизненного цикла” событий локации: pending/resolved/expired + 0..N событий на локацию.

## P0 (немедленно): система событий локации + DM‑тулзы проверок (минимум, который должен “просто работать”)

### P0.1. Событие локации = структурированный объект
- При входе в локацию генерировать 0..N событий (обычно 0..1).
- Минимальный payload:
  - `id`, `location_id`, `created_at`, `status` (pending/resolved/expired)
  - `hook` (1–2 строки)
  - `options` (2–4 действия игрока)
  - `suggested_checks` (0–2 рекомендаций: ability/skill, диапазон DC, критерий успеха/провала)
  - `stakes` (что меняется при success/failure)
- Принцип: `suggested_checks` — **подсказка**, а не обязанность.

### P0.2. Единый DM tool “запросить проверку”
- Стандартизировать сигнатуру (существующий или новый):
  - `request_ability_check(ability_or_skill, dc, reason, stakes, advantage_state, visibility)`
  - (опционально) `on_success` / `on_failure` как *короткие* системные цели, не как “готовый текст ответа”.
- Требования:
  - tool возвращает **задачу игроку** в **текстовом виде** (без кнопок): что проверяем, DC/ставки (кратко), и как бросить,
  - система сохраняет **ожидаемую проверку** в сессии, чтобы следующий бросок привязался корректно.

### P0.3. Бросок игроком (только текст)
- Когда есть pending check, бот ожидает один из вариантов:
  - `/roll` (по умолчанию d20) или `/roll d20`
  - (опционально) свободный текст: “бросаю d20”, “roll d20”, “кидаю с преимуществом” — парсится в тот же механизм
  - (опционально) “результат 17” (ручной ввод для оффлайн‑кубиков) — если разрешено
- Вывод результата: \(d20\) + модификатор + итог + пометка advantage/disadvantage.
- Важное правило: DM **не печатает** таблицы DC/“инструкции по проверкам”/списки “predefined checks” игроку; это внутренние подсказки DM или данные tools.

### P0.4. Runtime guardrails против “спама проверок”
- **Budget**: ограничение “существенных” проверок на сцену/короткий промежуток.
- **Cooldown**: не повторять один и тот же тип проверки в той же сцене без эскалации ставок.
- **Anti‑trivial**: низкие ставки → без броска (описание/автоуспех).
- **Reason+Stakes required**: обязательны и пишутся в историю.

### P0.5. Разрешение проверки и последствия
- После броска система возвращает DM структурированный результат (success/failure/crit + контекст).
- DM описывает исход и при необходимости применяет последствия инструментами (лут/подсказка/путь/бой/world event).

### P0.6. Запись в историю/RAG
- Событие локации → запрос проверки → бросок → исход должны индексироваться, чтобы DM “помнил”, что уже проверяли и чем кончилось.

## P1 (после P0): качество и UX‑шероховатости

### P1.1. Скрыть технику tools от игрока
- Игрок видит только художественный текст + понятный итог (“Ты выбросил 14: d20=11 +3”).
- Любые служебные строки (“выполняется проверка…”, `request_ability_check`, “ожидаемый ввод /roll…”, JSON/metadata) должны **отсекаться/переформулироваться** до отправки игроку.

### P1.2. Починить `/battlefield`
- Прозрачность боя и удобный дебаг.

### P1.3. Стабильность JSON и “безымянные враги”
- Меньше repair/fallback, бой не ломается из‑за пустых полей.
